# Architecture Overview

System map for Moony: stack, data flow, canonical examples, and the domain map.

## Stack

- **Tauri 2** — Rust backend; the `#[tauri::command]` handlers live in `src-tauri/src/commands/` (`mod.rs` contains none).
- **React 19 / TypeScript** — frontend.
- **SQLCipher-encrypted SQLite** — single baseline `001_initial_schema` plus append-only migrations in `src-tauri/src/db/migrations.rs` (see `docs/architecture/database.md`).
- **wouter** — routing (not React Router).
- **TanStack React Query** — all server state; no Redux/Zustand.
- **shadcn/ui** (new-york) + **Tailwind** — UI components and styling.
- **react-i18next** — ten locales (en, cs, de, es, it, nb, pl, sv, ja, zh), one namespace per domain.
- **sonner** — toasts.

## The Sacred Data Flow

Every feature follows this path — no layer-skipping:

```
UI component (src/pages/, src/components/<domain>/)
  → hook: src/hooks/use-<domain>.ts (useQuery) + use-<domain>-mutations.ts (useMutation)
    → src/lib/tauri-api.ts — <domain>Api namespace (the only place app commands are invoked)
      → #[tauri::command] in src-tauri/src/commands/<domain>.rs (thin)
        → business logic in src-tauri/src/services/<domain>.rs (takes &Connection)
          → SQLCipher SQLite
```

To see the flow end to end, read the bonds domain top to bottom: `src/pages/Bonds.tsx` → `src/hooks/use-bonds.ts` + `use-bond-mutations.ts` → `bondsApi` in `src/lib/tauri-api.ts` → `src-tauri/src/commands/bonds.rs` (minimal CRUD, so the command talks to SQLite directly). For the cleanest command → service split, read budgeting (`commands/budgeting.rs` → `services/budgeting.rs`) — backend only: its UI calls `budgetingApi` via inline `useQuery`/`useMutation` instead of dedicated hooks, which is exactly the layer-skipping this diagram forbids.

## Canonical Examples to Copy

When building something new, copy these — never the outliers:

- **Thin command + service + tests:** `src-tauri/src/commands/budgeting.rs` + `src-tauri/src/services/budgeting.rs` (`#[cfg(test)]` at the bottom).
- **Minimal CRUD domain:** `src-tauri/src/commands/bonds.rs` + `src/hooks/use-bonds.ts` + `use-bond-mutations.ts`.
- **Mutation hook with correct cache invalidation + snapshot:** `src/hooks/use-bank-account-mutations.ts`.
- **Dialog/form page pattern:** `src/pages/Loans.tsx` (lifted dialog state via `useState`) + `src/components/loans/LoanFormDialog.tsx` (react-hook-form + zodResolver).

## Currencies and conversion (ADR 0012)

Native amount, currency and date are the stored facts; there is no base currency and no stored
converted total. A monetary command takes the report currency (the main currency, chosen by
the frontend) and returns it as `currency` with an `fxQuality` (`missingCurrencies`,
`missingCount`, `estimated`); converted amounts are decimal TEXT at the currency's ISO minor
unit, `null` when not convertible.

- **One policy.** `services/fx.rs` converts: same currency is identity without a quote; a current
  conversion uses one `Quotes` snapshot; a historical one (`History::convert_on`) uses one UTC day
  that quotes both currencies, on or before the requested day, at most ten days back. `shared/fx.ts`
  mirrors it for the frontend and both are pinned by `shared/fx-test-vectors.json`.
- **EUR reference.** `exchange_rates` and `exchange_rate_history` hold units per 1 EUR; the
  reference is internal to `fx.rs`. AED, SAR, QAR, BHD, OMR (per USD) and BGN (per EUR) are derived
  at read time from `shared/fx-supported.json` and never stored. Source quotes plus derived codes are
  the 36 currencies allowed as the main currency; entity currencies stay free.
- **Missing is explicit.** An item that cannot be converted stays visible natively, the totals
  leave it out and name its currency; nothing is valued 1:1. `estimated` marks a cost that used
  today's rate because its own day had no common quote.
- **Frontend.** `useCurrency()` exposes the main currency, the snapshot `fx`, `fxRevision`, `fxReady`
  and `convert` (`null` without a rate); `useFxSnapshot` / `useFxHistory` (`src/hooks/use-fx.ts`)
  load quotes. Backend-computed pages format the response currency; pages that sum native entities
  convert with `convert`. Query keys of converted data carry the currency and `fxRevision`;
  `invalidateAfterPriceRefresh` (`src/lib/price-refresh.ts`) refreshes every price- and
  rate-dependent query after a refresh.

## Bank flow semantics

`services/financial_semantics.rs` shares account identity and meaning across categorization
and actual reports. Load `AccountIdentities::load(conn)` for each report so adding, editing
or deleting an own account changes automatic recognition of existing transactions.
Precedence is an explicit transaction `flowKind`, then known own account, then category
`kind`, then credit/income or debit/expense. Category-only updates preserve `flowKind`;
setting it to null restores automatic derivation. Own-account detection precedes merchant,
country and learned categorization rules. It never uses equal amounts or personal names.

Valid IBANs normalize whitespace/case. Valid Czech domestic identifiers require a bank
code, and normalize to their IBAN identity (including padded prefix/account and national
checksums). Optional structured bank codes can complete domestic identifiers; missing
codes are never guessed. Other identifiers stay verbatim. A domestic number written as sort
code, routing number or BSB plus account is a second own-account identity next to IBANs
(`account_number_key`: digits only, 11 to 34 of them, never letters, never a Czech
`prefix-account`; matched whole or as account plus a bank-code column); a bare short number
(an 8-digit UK or 9-digit US account exists at many banks), an incomplete Czech number and
opaque foreign routing values cannot establish an own-transfer identity. Expense credits are negative
expenses (refunds), income debits are negative income (reversals); `signed_flow_amount`
keeps these signs. There are three roles: income, expense and transfer (money moved between
the user's own pots: investing, saving, account transfers). What the money is lives in the
category; the role only decides how it counts (migration 010 collapsed the former investment,
financing and adjustment roles into transfer).

Own transfers without an identifier are recognised by rule-pack wording (`global` for English
own-account and credit-card wording, country packs for dialect and issuer brands; all
`cat_internal_transfers`). Pack priorities form tiers, highest first: 60 brokers, 50 and up
merchants, 45 mortgage, interest and card-issuer-charge guards (`gb/cc-fees`, `kr/deposit-interest`),
44 own-transfer wording, 40 ATM, 30/31 generic `kw-*` keywords. So "Transfer to Vanguard" stays
an investment and "BARCLAYCARD ANNUAL FEE" is a fee, not a repayment (the UK issuer brands are
the one bare-brand exception, and exactly why their guards exist). Other wording must name an
action (transfer, deposit, repay), never a bare product word that also appears on interest,
fee or earnings lines; "card payment", direct debit, standing order, faster payment, Zelle and
Venmo are deliberately not own transfers. Matching runs on folded text (`fold_for_rules`:
`fold_text`, which decomposes Hangul and kana, plus `ø æ ł đ ß œ` written as `o ae l d ss oe`, so
packs spell `lonn` and `haevning` in ASCII) while a `regex` pattern is compiled as written apart
from those letters, so Hangul rules must be `contains` (both sides are folded, so a short Hangul
rule matches inside longer words: interest is matched as phrases such as `예금이자`, never as the
bare `이자`, which is in "이자카야" and "...페이자동...") and a regex may only contain characters
that fold to themselves (no diacritics, Hangul or voiced kana marks). Learned-payee keys keep
plain `fold_text`.

## Bank statement import (ADR 0019)

A bank file takes one of two routes into one shared core. `statement_import::detect` reads the
first 4 KB and decides from the content, never from the extension. `inspect_statement_file`
returns `null` for a file that is none of the statement formats, and the dialog then runs the
CSV steps unchanged.

```
file bytes ──► statement_import::detect ──► None ──────────────────► CSV path: parse_rows
                       │ Some(format)
                       ▼
        decode ──► parser (camt.rs, mt940.rs, ofx.rs, qif.rs) ──► Vec<Statement>
                       ▼
        merge (same account and currency) + account match + balance check
                       ▼
        to_rows ──► ParsedImport { rows, period, declared_balance }
                       ▼
     csv_import core: preview_rows / import_rows   ◄── CSV path ends here too
        duplicate check → category (override → source map → rules)
        → insert_batch → create_transaction_with_origin → finish_batch
```

`services/statement_import/` holds `detect` and `decode` (format and encoding), `model` (the
neutral `Statement` and `Entry`), `camt` on `xml_tree` (a small tree over `quick-xml` events,
elements matched by local name), `mt940` (a tag stream and SWIFT envelopes; the `:86:` text is
read in one of three dialects chosen from its shape: subfields, `/TAG/` pairs or free text),
`ofx` (a tag scanner of its own for OFX 1.x SGML and 2.x XML, whose elements are not always
closed, building the same `xml_tree::Node` tree as CAMT; bank and credit card statements are
imported, investment statements are refused or warned about),
`qif` (a two-pass scan: the records are sorted into their accounts first, then the whole file's
dates and amounts decide the date order and the decimal separator once; the order is detected
with `date_parser::detect_date_format` and `StatementImportOptions.date_order` overrides it, and
`StatementInspection.date_order_ambiguous` tells the dialog to ask),
`decimal` (exact decimal arithmetic for the balance check, never `f64`), `merge`,
`account_match`, `to_rows` and `types` (wire types). `mod.rs` is the service
the three commands call (`inspect_statement_file`, `preview_statement_import`,
`import_statement_file`). Parsers are pure functions from text to statements. The core never
learns which format a row came from, so duplicate checks, categorization, the batch record and
undo are the CSV ones, and the write path is `create_transaction_with_origin` (ADR 0007).

For statement files `line` is the 1-based ordinal of the entry in the selected statement. Fixtures
are synthetic files under `src-tauri/tests/fixtures/statements/<format>/` (see "Adding a statement
fixture" in `CONTRIBUTING.md`). The dialog is `StatementImportDialog.tsx` in
`components/bank-accounts/`, the CSV steps live in `csv-import/`.

## Bootstrap & Auth

Provider nesting from `src/App.tsx` (outermost first):

```
QueryClientProvider → AuthProvider → ThemeProvider → I18nProvider → CurrencyProvider → SyncProvider
  → TooltipProvider → ErrorBoundary → UpdaterProvider → AppLayout (AppShell → Router)
```

- Auth states: `needs_setup | locked | unlocked`.
- `SyncProvider` refreshes stale prices 5 seconds after unlock (`setTimeout(runStartupSync, 5000)` in `src/hooks/SyncProvider.tsx`), then queues the history rebuild (`start_snapshot_backfill`, see "History recalculation"); it invalidates the relevant React Query caches when a rebuild batch completes.
- `UpdaterProvider` (`src/hooks/use-updater.tsx`) is the only updater: one automatic GitHub check per session, 5 seconds after unlock, only while the device-level setting `moony-auto-update-check` is on (Settings → Security → Updates); the badge, the update dialog and About all read it.
- Desktop biometric unlock (macOS Touch ID, Windows Hello; ADR 0021): the `moony-keychain` plugin's desktop backend (`plugins/moony-keychain/src/desktop/`) wraps the master key with a Secure Enclave key (`macos.rs` + the `MoonyBiometrics` Swift package, linked with swift-rs) or a Hello signature (`windows.rs`, `hello_wrap.rs`) and keeps the blob in `moony.master-key.bin` in the data folder (`blob_file.rs`); Linux answers `Unsupported`. The commands and `services/biometric_unlock.rs` are the phone's, shared; on macOS and Windows `SessionKey` holds the master key for the unlocked session (Linux keeps nothing). Only an `Invalidated` answer switches the feature off. The frontend: `src/lib/biometrics.ts` (status, the `moony-biometrics-asked` flag), `EnableBiometricsDialog` (one-time offer after a password unlock), the lock page (one automatic prompt when the app starts, none after a lock; a button opens it otherwise) and the switch in Settings → Security. Restore switches it off in Rust; account deletion removes the stored key. The blob is never in a backup or the export.
- Auto-lock: `useAutoLock()` (`src/hooks/use-auto-lock.ts`, mounted in `AppLayout`) locks the app after N minutes without input and on wake-up once the deadline has passed; the device-level setting is the `localStorage` key `moony-auto-lock-minutes` (off / 5 / 15 / 30 / 60, default 15), edited in Settings → Security (`AutoLockSlot`); deadline logic is pure and tested in `src/utils/auto-lock.ts`.

## History recalculation

Every past day of `portfolio_metrics_history` is derived from dated facts (ADR 0016); a write that changes a past day queues a rebuild and returns, and one background worker re-derives the days.

- **Queue.** `services/history_recalc.rs` holds three job kinds, each carrying the earliest affected day: `StockTicker` and `CryptoTicker` rebuild one ticker's value history from quotes, `Days` re-derives the portfolio days. The queue keeps one entry per key and the earliest date, so a bulk delete or an import costs one rebuild per ticker, and work queued during a run joins the next batch. Jobs dated today or later are dropped (today's row belongs to the live snapshot, `update_todays_snapshot`).
- **Worker.** One batch first extends the exchange-rate history over any missing range (`fx_backfill::ensure_fx_coverage`; no request when nothing is missing), then rebuilds the stock tickers (Yahoo), then the crypto tickers (Yahoo Finance's daily closes, one request per ticker for the whole range, the symbol read from `crypto_investments.yahoo_symbol`; a holding without a symbol is resolved first when Yahoo can tell which coin is meant (`services/crypto_symbols.rs`) and is skipped otherwise; every gap, an unresolved coin, no Yahoo quote or offline keeps the last known price), then re-derives the days from the earliest date of the whole batch, so a ticker job needs no separate `Days` job. Quotes are fetched without the database lock; `services/ticker_history.rs` plans a ticker's rows in one pass (running position, FX rates preloaded; about 0.09 s for a 630-day ticker, `cargo test --lib ticker_history::golden::benchmark -- --ignored --nocapture`). A failed ticker is logged and reported `failed` without stopping the days rebuild. Held tickers without a row in the batch window get a quote lookup too, but only a ticker held in that window (a position at its start, or a trade inside it): a holding sold out before it never costs a provider call. A batch that panics marks the queue idle again (`WorkerGuard`), so later rebuilds are not stalled.
- **`rebuild_days`** (`services/history_days.rs`) reads every fact once and writes one row per day from the earliest dated fact (`earliest_fact_day`, never before 2000-01-01) to yesterday, in 60-day chunks, each its own transaction and lock hold, with the worker yielding between chunks, so reads are served throughout. It is idempotent, deletes backfill rows before the first fact, and runs under one gate shared with the durable MCP worker. All writes go through `services/portfolio_history.rs`, the single writer of the table.
- **Class rules.** Savings take the newest balance record on or before the day and count nothing before the first one (an account without records is undated); loans are always the ledger walk `loan_balance_at` on every day before today (0 before the start, the estimate until the first manual balance record, then the manual records hold): they are computed values, so a live row's recorded loans are rewritten too and no live-row guard or remainder applies to them; real estate counts from the purchase date and not at all without a valuation: its value is a straight line through the points of the property, the purchase (`purchase_price`, when the purchase date precedes the first valuation day) and every valuation (of several on one day, the last created), straight between two consecutive points of one currency, the earlier value held until the next point when their currencies differ, and the last value held after the last point (`Property::value_on` in `history_days.rs`, mirrored by `valuationTrace` in `src/utils/valuation-trace.ts` for the detail chart, so today's value, the newest valuation, stays consistent); other assets are the quantity their transactions leave times that day's valuation (one with a quantity and no transactions is undated, like an account without records); a bond counts `coupon_value × quantity` from its purchase date on and nothing before it (one without a purchase date is undated, like an account without records); stocks and crypto come from the ticker histories. A backfill or new row gets all eight breakdowns, and what the facts do not date (undated items) is the "unknown remainder" of the nearest live row that counts the same items as the day, `recorded - derived` per class and currency, so a class does not jump between rebuilt and live days and no item is counted twice (the undated items at today's value only when no live row qualifies; a class the facts cover on a day takes no remainder; the code is `LiveRemainder` in `history_days.rs`). A live row is rewritten only for the classes the facts cover completely that day (undated accounts, undated other assets and undated bonds are not), stocks, crypto and loans always. A dated bond counts from its purchase date for the remainder rule too, so a live row before it does not hold it.
- **Triggers.** UI write commands (`bank_accounts`, `investments`, `stock_import`, `crypto`, `other_assets`, `real_estate`, `loans`, `bonds`, and a symbol change in `crypto` (`set_crypto_symbol`)) queue their jobs through `portfolio::schedule_history_rebuild`. A write to a **static class** (bank accounts and balance records, real estate and valuations, loans and their events or manual balances, bonds, other assets with their transactions and valuations: create, edit, delete) always queues `Days(0)` (`history_plan::all_days`); `plan_rebuild` clamps it to the earliest fact, and a days-only rebuild is local and cheap. The day of the edit is no bound on the days it changes: a day the facts do not cover takes the remainder of a live row (`recorded - derived`), and `derived` moves with every item, so one change (a purchase date set on a property, a first balance record, a valuation) can change every earlier day (a rebuild from the edit's day left the old remainder on the days before it, a cliff on the purchase day). `services/history_plan.rs` only decides whether an edit touches a fact the history reads (a rename or a note queues nothing). Only `StockTicker` and `CryptoTicker` jobs, which cost a network fetch, keep the earliest affected day. MCP write tools record a durable follow-up (domain and earliest day, ADR 0014; a follow-up without a day is "from the first fact" and wins over dated ones queued next to it) and the worker in `commands/mcp_refresh.rs` runs it: tickers strictly, so a provider failure keeps the intent pending, then `rebuild_days_async`; the static domains (`other-assets`, `bank-accounts`, `real-estate`, `loans`, `bonds`) rebuild every day from the first fact whatever day the follow-up holds.
- **Startup.** `start_snapshot_backfill` (called by `SyncProvider` after unlock) only plans and queues, then returns. Below `app_config.history_rebuild_version` 4 it queues every ticker from its first transaction plus `Days` from the first fact; the version is stored once the days rebuild succeeded, whatever the tickers did (a ticker the provider keeps rejecting is retried by later writes, not by every start). Version 1 was the first rebuild from dated facts; version 2 repeats it for profiles that ran version 1, whose days a date-precise static trigger may have left on an old remainder and whose crypto days older than the provider's one-year window held one stale price; version 3 repeats it once more for profiles that ran version 2, whose loan days (backfill and live) carried a phantom remainder taken from a live row that the old valuation model had recorded, because loans are now always derived from their ledger; version 4 repeats it for stock splits, whose full-range fetch records the splits Yahoo reports and stores split-adjusted closes (a stock rebuild that records a new split after its window started queues the ticker again from its first transaction). Otherwise it queues the held tickers and the days from the first missing day. `recalculate_all_portfolio_history` queues the same as the one-time rebuild.
- **Events.** `history-recalculation` `{ ticker, status: 'running' | 'done' | 'failed' }` per ticker (the header's `HistoryRecalculationBadge` shows a running rebuild; on done or failed it refetches `portfolio-history`, `ticker-history` and `stock-performance`), and after each finished batch `recalculation-complete`, on which the history charts and position views refetch. A days-only batch has no ticker, hence no status event.

## Device sync (hidden until release)

Device sync (spec `docs/specs/2026-11-06-device-sync-client-design.md`, ADR 0024 for the merge, ADR 0025 for the relay client, ADR 0026 for pairing and the phone, ADR 0027 for the fixes after the security audit of 2026-11-11, ADR 0029 for own sync servers) is built and tested in every build, but nothing of it runs unless `services/sync/feature.rs` says so: `RELEASED` is `false` until the release phase, and a debug build has sync on unless `MOONY_DEV_SYNC=0`, at run time or in the environment it was built in (`option_env!`, for the iPhone, which gets no environment; the same for `MOONY_RELAY_URL`). A release build never reads `MOONY_DEV_SYNC` or `MOONY_RELAY_URL`, at run time or at build time (`a_release_build_ignores_the_dev_variables`, run with `cargo test --release`). With the flag off, Settings shows no Sync section, the top bar no sync indicator, and every sync command answers `validation.syncUnavailable` except `sync_feature_enabled`, the read-only `sync_profile_state` and `sync_turn_off`: a profile that had sync turned on in a development build is still captured in a build without the flag (its changes are recorded, never sent), and a leftover card (desktop Settings → Data, a row in the phone's settings) turns sync off (audit M12, ADR 0027).

- **Capture or guard.** An enabled profile either captures every change of its synced data or refuses to change it (`capture/guard.rs`, ADR 0027): when capture cannot be installed at unlock, `sync::on_open` marks the profile capture-broken and imposes a guard on the connection (an SQLite authorizer, a marker function and TEMP triggers for the synced `app_config` keys) that refuses writes to synced data with `validation.syncChangesPaused`, and falls back to `PRAGMA query_only` if the guard cannot be imposed. Local columns and tables, `sync_devices`, backups, a repair and turning sync off keep working. The guard holds one connection: every connection to a profile must be opened through `Database::open_with_key`, which runs `on_open`. A guarded or read-only profile counts as capture-broken and runs no round.
- **Engine.** `engine/runtime.rs` runs one task per unlocked profile (started at unlock by `commands/sync.rs`, stopped at lock, restore and Delete Account). It checks the restore marker and the this-machine binding first (a binding that cannot be checked stops the start with the problem `secureStorage`; the third such app start in a row re-joins), then runs rounds (`engine::run_round`: pull, push, snapshot) on unlock, local writes (the outbox polled every 5 s), every 5 minutes and "Sync now", with a back-off on failures. Status reaches the UI as `sync-status-changed`, merged changes as `sync-data-changed`.
- **Documents and photos (ADR 0030).** Attachment rows sync like any row and are never held for their content; the content moves separately, encrypted per blob (`blobs/`: `stream.rs` streams 64 KiB chunks between `attachments.db` and the wire, `transfer.rs` moves one blob, `policy.rs` holds what the transfers share). The Local queue `sync_blobs` (`blobs/queue.rs`) is reconciled from the rows and the store: `up` held here and not confirmed by the server, `down` named and not here, `done`. A round uploads content of at most 8 MiB that never failed an attempt before it pushes, within 20 seconds and only if the upload lane is free (`engine::upload_before_push`). Everything else goes through the two lanes `engine/runtime.rs` runs in a second task beside the loop, sharing the round's `BlobPolicy`: one upload and one download at a time, woken after every round, on "Sync now" (which also forgets the server's cached answer, ends the no-room pause and makes every backed-off entry due) and by `EngineHandle::wake_transfers`, and at least every 60 seconds. An engine's lanes wait on the profile's lane gate (`ConnAccess::lanes_lock`) until an earlier engine's lanes ended, then sweep incomplete blobs and reconcile the whole queue once before any transfer; stopping the engine stops them (lock, restore, Delete Account and every sync change wait for that, `stop_engine_and_wait`). They rest where the round does not sync (capture broken, vault gone, an unauthorized token, the binding check not passed) and while the round backs off after a failure; after a lapse or a rotated token downloads go on and uploads wait. A desktop fetches everything in the background, oldest row first; a phone fetches thumbnails at once and full content when it is opened or with "Download everything" (`BlobPolicy::for_this_platform`). What the lanes change reaches the app as `sync-attachments-changed` (no payload, at most four a second, the last change always told) and in `SyncStatus.attachments`.
- **The daily pass (ADR 0030).** Once per 24 h, after a `Normal` or `FirstSnapshot` round, a fully caught-up device lists the vault's blobs (`blobs/pass.rs`, from `engine::daily_pass`), deletes those no row here names or a replace holds that are older than 7 days by the listing's `now`, and queues for upload again the content it holds that the server lost; within 60 seconds, never failing the round; one that started and did not complete waits an hour unless "Sync now". Its mark is the Local `app_config` key `sync.blob_pass_at`.
- **Status.** Phases (`SyncPhase`): `off`, `settingUp`, `idle`, `syncing`, `waiting` (a change from another device is held; this device keeps syncing), `paused`, `error`. Problems (`SyncProblem`): `captureBroken`, `vaultGone`, `lapsed`, `quotaExceeded`, `snapshotTooLarge`, `newerSchema`, `gap`, `clockAhead`, `undecryptable`, `invalidChain`, `missingParent` (no longer produced), `quarantined`, `offline`, `relayError`, `rateLimited`, `unauthorized`, `keyRotated`, `secureStorage`, `serverWentBack`, `internal`; `engine/status.rs` maps each to its phase, and `src/utils/device-sync-problem.ts` to the action the UI offers.
- **One status mapping.** `src/utils/sync-state.ts` (`syncState`) turns a `SyncStatus` into the one state that the desktop top bar (`SyncStatusIndicator.tsx` and its popover), Settings → Sync and the phone's Settings row and sync block all show: synced, syncing, out of reach, out of reach for days, waiting, paused or error, each with a tone (fresh, neutral, stale). The server counts as out of reach only for the problems the engine retries by itself, `TRANSIENT_PROBLEMS` (`offline`, `relayError`, `rateLimited`). Out of reach for less than `SYNC_STALE_DAYS` (7 whole UTC days, counted from `lastSuccessAt`, else from `SyncStatus.enabledAt`, which is this device's own `sync_devices.joined_at`) is neutral, and Settings shows a plain line instead of an alert (`isQuietlyOutOfReach`); from the seventh day on it is stale. A running round shows as syncing. `sync-state-backend-pin.test.ts` keeps the threshold and the problem list equal to the Rust ones of the reminder below.
- **Stalled-sync reminder.** The milestone kind `sync_stalled` (`services/milestones/upkeep.rs`, in Údržba on the desktop and the phone) exists only while the sync flag is on (`commands/milestones.rs` reads the status for it). It is raised at once for a paused or failed sync whose problem is not one of `TRANSIENT_PROBLEMS`, and after `SYNC_STALE_DAYS` for a server out of reach; never for a status without a problem, however old its last success, and never while sync is off or being set up. Its key carries the day of the last success (or of `enabledAt`).
- **Joining from the first run.** With the flag on, the first run's first step offers "Already use Moony on another device?". The join path asks only for this device's password, creates the profile and shows its key as usual, then Připojení (desktop `components/auth/onboarding/ConnectStep.tsx` with the steps in `src/utils/onboarding-steps.ts`; phone `mobile/pages/first-run/ConnectStep.tsx` with the order in `mobile/lib/first-run.ts`) runs the same pairing and Recovery Kit join flows as Settings (`components/settings/sync/join/`), shaped by `src/utils/join-context.ts`: no password field, no replace warning and no impact list (the impact is still read for the consent), because the profile is brand new and its join backup stays plain (see "Replaces and their backups"). A join ends on the Overview with the synced profile's name, areas and accounts; "Continue without sync" falls back to the normal steps (Co sledovat with the name, then the first account). Settings → Sync without sync offers "Start syncing" and "Connect this device"; the latter opens `JoinDeviceDialog`, with the replace warning and the impact list.
- **Holds and skipping.** A gap in an author's chain, a change whose parent never arrived and a change dated more than 10 years ahead are held: the cursor stays before them, other authors apply and this device keeps pushing (`engine/pull.rs`). `chain/gaps.rs` keeps one Local record per held author (`app_config` `sync.held_gap.<device hex>`); after 14 days Settings offers "Skip the missing change" (`commands/sync_gaps.rs`: `sync_held_gaps`, `sync_skip_missing_change`, behind the password), and the miss travels in this device's snapshot headers until a clean snapshot heals it (`sync.skipped_miss`).
- **Echo.** A push answer deletes nothing: an envelope stays in `sync_unsent` until this device's own pull sees it back, every push sends the unechoed ones again first, and a round that pushed pulls once more for the echo (`engine/push.rs`, at most 1,024 unechoed). An envelope that never comes back shows `relayError`. A sync server whose head goes below a device's place (one restored from an older backup) sets the sticky `sync.vault_went_back_at` and shows `serverWentBack` until a replace or turning sync off; nothing repairs it automatically (ADR 0027 lists the manual recovery).
- **Replaces and their backups.** A join, repair or re-sync (`join.rs`) asks `sync_replace_impact` for what it puts at stake, shows it in the confirmation and sends that consent back; the backup and the replace run in one connection hold and only within the consent (`impact.rs`, `validation.syncReplaceImpactChanged` otherwise). A join into a brand-new profile (`impact::brand_new_profile`: no account, transaction, document, photo or unsent change counted, no watchlist entry, budget goal, spending plan, planned cashflow item, own rule or category or stock tag, and created less than 24 hours ago) writes its backup as usual and leaves it plain (prunable), spec 2026-11-14 §5.4. Documents and photos are synced rows (ADR 0030), so after a replace their rows are the vault's; content this device holds under a blob ID a vault row names is kept, and this device's rows the vault lacks are counted as orphaned and remain only in the backup (`snapshot/attachments.rs`); the content of every blob this device's rows named before the replace is held until the first pull after it caught up, because a row pushed after the vault's snapshot comes back only with that pull (`held_blobs.rs`). The backups (`backups.rs`: `sync-repair-<unix>[-n].zip`, `-kept` never pruned, `-unused` when the replace did not happen) are listed under Restore (`commands/sync_backups.rs`: `sync_list_backups`, `sync_delete_backup`, and on iOS `stage_sync_backup_export` for a copy to Files).
- **Relay.** Every request goes through `relay/http.rs` to the address stored in `sync_state.relay_url`, the only stored value that names the sync server; `MOONY_RELAY_URL` only supplies the default address before an account exists, in debug builds. `http` is accepted for any host but the Moony cloud, in every build (`scheme_allowed`, ADR 0029); the dialogs warn each time.
- **Own sync server (ADR 0029).** Setup takes a connection code (`connection_code.rs`: `moony-sync1:<account>:<base64url address>`; `server_address_from_input` takes a code or an address) and adopts the account the server's admin created (`setup::connect_own_server`, commands `sync_check_server` and `sync_connect_own_server`). Before an address is used, `server::check_own_server` asks `GET /v1/server` (`MIN_PROTOCOL = 2`). The join dialogs take an address or a code, and a plain-`http` host that is not loopback needs a ticked warning. Settings → Sync shows the server and an "unencrypted" note, and "Change address" (`sync_change_server_address`, password required, `server::change_server_address`) swaps `relay_url` only after the stored account, the stored vault with its token and `head >= cursor` check out at the new address. `SyncStatus.ownServer`, `serverAddress` and `serverInsecure` come from the stored address. The Moony cloud card is disabled and its setup branch is unreachable.
- **Pairing.** Protocol 2 (ADR 0026 as amended by ADR 0027). `pairing/mod.rs` holds the bytes (the `moony-pair:2:` QR text, slot 1, the HKDF transcript with the six-digit code and the acknowledgement key, the sealed slot 2, the acknowledgement in slot 3, the cancel marker, the typed-code check; vectors in `pairing/tests.rs`), `pairing/session.rs` the state machine over the relay's three-slot mailbox (`relay::Mailbox`, served by `relay/http.rs` and the in-memory `relay/fake.rs` with `relay/fake/mailbox.rs`). The scanning device shows anything only after the showing device's acknowledgement in slot 3 verifies; only the joiner shows the six digits, and the person types them on the holder (`sync_pairing_confirm(typedCode)`, three attempts). Slot 3 needs a sync server built from the relay branch `feat/pairing-ack`; an older server answers `bad_slot`, shown as "this sync server needs an update", so every self-hosted server (the home server included) must be redeployed before pairing works there. `commands/sync_pairing.rs` keeps one pairing per app in a slot bound to the profile session, checks the device password before a QR is shown or slot 1 is written, wipes received credentials when they expire, and gives the pairing up at lock, restore, Delete Account, and turn-off or deletion of the synced data while sync is on (`forget_pairing`). The desktop always shows the QR ("Add a device" with sync on, "Join from your phone" without), and the phone always scans; two desktops or two phones join with the Recovery Kit (`sync_join_with_recovery_kit`). A join (`sync_pairing_join`, `join::join_new_device`) stops at a "Join and replace" confirmation with what it puts at stake, then backs up and replaces this device's data as a sync change, under the desktop's busy modal or the phone's busy cover. Pasting a pairing code is a developer tool only (ADR 0026).
- **Recovery Kit.** Every showing needs the device password (`sync_prepare_recovery_kit`, `sync_show_recovery_kit`); copying and saving need the 5-minute window it opens. The desktop saves the Kit from Rust (`commands/sync_kit.rs`, `kit_file.rs`: the save dialog, an owner-only file, a warning for cloud-synced folders) and protects the window from screen capture while it shows (`use-recovery-kit-lifetime.ts`); the Kit leaves the screen after 5 minutes or when the app is hidden.
- **Devices.** `sync_list_devices` (`devices::list_devices`) lists the account's devices; "Last change synced" is derived from the newest clock each device wrote, never stored, and a device with no change in more than 30 days gets a neutral "No changes from this device in N days" marker (`src/utils/sync-devices.ts`). The list and the Kit screens say that a lost device or Kit cannot be cut off yet (no removal until phase 5). `sync_rename_device` renames this device as a synced write.
- **Mobile.** Wired: `MobileShell` mounts the sync events and the busy cover, and Settings → Sync (`mobile/pages/settings/SyncSection.tsx`, `mobile/components/sync/`) shows the status, the devices, the Recovery Kit, scanning (the camera through the barcode-scanner plugin, `windowed` under the app's own overlay; `mobile/lib/qr-scanner.ts`, `mobile/lib/sync-scan.ts`) and a first-device setup from a connection code (the setup never opens a checkout, spec §16a Q4; ADR 0029). The iPhone's binding is a Secure Enclave key, as on macOS, and the recovery code goes to a `.localOnly` pasteboard that expires after 60 s; Android answers `Unsupported` for both.
- **Run it against a local sync server.** The server is the Node sync server of the Moony-relay repository (its `README.md` and `DESIGN.md` are authoritative). Build it (`npm run build`) and start it with a throwaway data folder and a fixed setup code: `SETUP_CODE=moony-e2e-setup-code DATA_DIR=$(mktemp -d) npm start` (port 8787). In its admin (`http://127.0.0.1:8787`) set up the admin, save the address and add a person; the person's connection code is what the app's setup takes. Then, with a demo profile (never a real one), `npm run tauri dev` and Settings → Sync → Set up (a debug build has sync on by default since 2026-11-14; `MOONY_DEV_SYNC=0` turns it off, a release build stays without it until `feature::RELEASED`). Plain `http` to any host except the Moony cloud is accepted in every build, with the warning for a non-loopback host.
- **Pair two devices locally.** With the sync server and the desktop running as above (sync set up on the desktop, or not, to join it), start the simulator: Xcode's build phase drops shell variables, so put an uncommitted, gitignored `.cargo/config.toml` at the repository root with `[env]` `MOONY_RELAY_URL = { value = "http://127.0.0.1:8787", force = true }`, touch `src-tauri/src/services/sync/feature.rs`, and run `npx tauri ios dev "iPhone 18 Pro" --config src-tauri/tauri.mobile-dev.conf.json` (`npm run ios:dev` names a simulator Xcode 27.1 does not ship). Delete the file afterwards; it points every debug build and test in the checkout at that server. The simulator shares the Mac's loopback, so it reaches the sync server on `http://127.0.0.1:8787`, but it has no camera and takes no paste or typing from the Mac: drive the phone through the dev bridge instead, by opening `http://localhost:1430` in a browser (it runs the phone shell and relays every command to the simulator's backend) and calling `deviceSyncApi.pairingScan(code, { password, deviceName })`, `pairingPoll()`, `pairingConfirm()` and `pairingJoin(consent)` from its console, with the code from the desktop's "Add a device" (the dev build's `pairingPoll().pairingCode`). Only the joiner shows the six digits (on the phone `pairingPoll().comparisonCode`) and continues with `pairingConfirm()`; the holder types them (on the desktop in the dialog, on the phone `pairingConfirm('123456')`). The join's consent is `{ changesThrough, attachments }` from `deviceSyncApi.replaceImpact()` (its `changesThrough`, and `documents + photos`; `consentOf` in `src/utils/replace-impact.ts`). The phone shell's rows answer touch, not mouse clicks, so the browser cannot tap them. Two desktop dev builds (the second with its own `HOME` and Vite port, as the demo launch configurations do) cannot pair, since a desktop never scans; they test the Recovery Kit join.
- **End-to-end tests** against that server (`#[cfg(test)]` and ignored by default; the pairing and join tests are in `relay_e2e_pairing.rs`, documents and photos (the blob calls, two devices, a join, the daily pass, a quota refusal, an upload the server already has) in `relay_e2e_blobs.rs`, and both run with the same filter; `relay_e2e_blobs` alone needs a server with the blob routes, its header has the recipe): `cd src-tauri && MOONY_RELAY_E2E=http://127.0.0.1:8787 cargo test --lib relay_e2e -- --ignored --test-threads=1`. `MOONY_RELAY_E2E` names the server's address; `MOONY_RELAY_E2E_SETUP_CODE` its setup code if it is not `moony-e2e-setup-code`. The suites go through the admin as a person who runs a server does (`relay_e2e_admin.rs`: set up or sign in, add a person, block, unblock, delete) and set up from the person's connection code; the header of `services/sync/relay_e2e.rs` has the recipe. The server limits account lookups to 60 a minute per client address, so the suites wait and retry on `RateLimited`.
- **iOS binding self-test.** `cd src-tauri/plugins/moony-keychain/ios && xcodebuild test -scheme moony-keychain -destination 'platform=iOS Simulator,name=iPhone 18 Pro'` runs the Swift side: the ECIES and blob format with a software key, the failure reports, and the Secure Enclave round trip where `SecureEnclave.isAvailable` (the Xcode 27 simulator included). Rust classifies the failures (`moony-keychain`'s `classify_ios_binding`, covered by `cargo test`).
- **Capture measurement.** In a debug build with the flag on, `await window.__TAURI_INTERNALS__.invoke('sync_debug_capture_overhead', { rows: 5000 })` in the web inspector times a statement import with and without change capture.

## Logging

`log` macros go through `tauri-plugin-log` (`src-tauri/src/services/logging.rs`) to `moony.log` in the OS app-log directory — macOS `~/Library/Logs/com.moonyfinance.desktop/`, Windows `%LOCALAPPDATA%\com.moonyfinance.desktop\logs\`, Linux `~/.local/share/com.moonyfinance.desktop/logs/` — UTC timestamps, `info` in release / `debug` in debug builds, 2 MB per file with two dated archives kept. The `open_logs_folder` command reveals the folder; panics are logged too.

## Outbound HTTP

ECB rates, Frankfurter history, the Yahoo coin search and the stock logo lookups (Yahoo search, then the logo images from `s.yimg.com` or Financial Modeling Prep, ADR 0031, the images with redirects disabled) go through one shared `reqwest::Client` (`src-tauri/src/services/http.rs`: 15 s connect + total timeout, `User-Agent: Moony/<version>`). Yahoo Finance chart requests (stock and crypto prices and history) use the `yahoo_finance_api` connector, built with the same 15 s bound in `services/price_api.rs`. Never call `reqwest::get` (no timeout). Device sync's relay client (`services/sync/relay/http.rs`) uses the shared client with redirects disabled (`services::http::no_redirect_client`), caps every answer body and raises the bound per request only for push and pull (120 s) and snapshots (600 s).

## Known Structural Debt

Fat command files hold logic that belongs in services (link, don't fix):

- `portfolio.rs`
- `projection.rs`
- `real_estate.rs` (costs, photos, documents and links)
- `cashflow.rs`

See `docs/DEPRECATED.md` for patterns not to copy.

Actual cashflow and budgeting use `services/reporting.rs` for the same booked ledger rows, dynamic own-account recognition, explicit flow overrides, signed refunds/reversals and strict recorded historical FX. Missing FX rows remain visible with a null contribution in the report currency and quality counts; they do not enter numeric totals. SQL read failures are errors. Report account scope is independent of portfolio exclusion. `netBalance` describes ordinary income less expense; `bankCashMovement` additionally includes signed transfers. Cashflow reports one calendar period (month, quarter or year) and groups income, expenses and transfers by category; uncategorized rows form their own group per role. Its chart window is the twelve months ending with the period's last month.

Observed completed months are a sample, not evidence of full statement coverage. Cashflow averages exclude partial/unobserved months and months with missing FX; the response names the actual average sample months. There is no comparison period. Planning remains a monthly/yearly equivalent estimate with its as-of date and current-FX quality; it uses loan amortization to omit repaid/expired loans and supports explicit replacement sources.

## Money flow review

The account ledger uses server filters and stable pages, while native summaries and balance estimates traverse every page and exclude pending or foreign-unit rows. Transaction details retain statement provenance and use the server effective-flow resolver. Cashflow and budgets share account scope, the period control, historical report-currency contributions, quality notes and counted drilldowns. The drilldown dialog recategorizes rows in place: it keeps the list it opened with (its query sits outside the refresh keys) and marks rows that left the line as moved while the report refreshes.

`src/lib/money-flow-refresh.ts` refreshes transaction/report/goal/drilldown domains and records a portfolio snapshot after writes, including external bank events. Category assignment awaits persistence. Learning is a separate opt-in for one account and direction, committed before changing engine memory; accepting a suggestion or picking a CSV category alone learns nothing. New scoped rows coexist with clearly labeled legacy broad learned rules.

Budget edits preserve original money text when unchanged and select an effective month. Report limits use historical versions, while edit/delete actions refer only to current goal IDs. Planning labels monthly-equivalent estimates and exposes explicit replacement links to automatic sources.

Ledger effective meaning stays unresolved while its server read is loading, missing a row or failing; failure exposes retry. Budget actuals consume every server-resolved expense category independent of fixed category IDs. The uncategorized expense drilldown uses a dedicated booked expense count (including missing-FX rows), preserving access when debit/refund contributions cancel without counting uncategorized income.
