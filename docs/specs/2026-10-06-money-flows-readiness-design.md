# Money flows readiness

Binding design for the autonomous implementation requested on 2026-10-06. Source: `docs/audits/2026-10-06-money-flows-audit.md` (A01–A19). This is a feature-tier change. Preserve the existing design system, privacy model, country packs, money-as-TEXT/CZK base, and both languages.

## Financial meaning

Transactions retain credit/debit and native currency. Add a nullable explicit `flowKind` override with values `income`, `expense`, `transfer`, `investment`, `financing`, `adjustment`; null means derive. Categories expose a persisted role (`kind`) using the same values; existing custom categories default expense, `cat_income` is income and `cat_internal_transfers` transfer. Credit in an expense role is a refund; debit in income reverses income. Reports share one resolver: explicit user flow first, then known own account, then category role, then credit=income/debit=expense. Resolve known own accounts at report time too, so adding an account recognizes old transfers without rewriting manual choices. Country/merchant rules cannot override own-account detection. Transfers and investment/financing/adjustments are visibly separated from ordinary income/expenses. Do not infer transfer from equal amounts or a matching personal name. Explicit flow can override automatic recognition; categorize alone cannot.

Normalize valid IBANs and Czech domestic identifiers, including bank code, into the same identity. Preserve other domestic/routing identifiers verbatim rather than pretending they are IBAN. Structured country/bank identifier fields in CSV are optional; never guess a missing bank code. A known one-sided transfer is valid; linked-pair/refund matching is optional metadata, not a prerequisite for excluding transfers. Unknown transfers can be classified explicitly. Category creation/edit offers the role.

Only booked transactions enter actual reports. Preserve signed refunds/reversals in totals, monthly values, groups and drilldowns. Report conservation: net=income-expenses plus separately reported nonconsumption flows. Totals and drilldowns must reconcile. Do not silently invent a 1:1 FX rate. Missing historical conversions are excluded from numeric totals and reported as incomplete, with currency/count; cached/current fallback, if used, must be labeled estimated. Keep portfolio conversion behavior outside these reports intact.

Account summaries must not add different currencies. Show currency-matching booked flows and an explicit excluded foreign-currency warning, or show separate currency groups. Never reconstruct a single balance from mismatched units. Balance updates carry an as-of booking date and currency; unknown legacy balance date is unknown, not updatedAt. A partial ledger's balance chart is an estimate. Old/mismatched statement balances cannot silently overwrite current balance. All transaction/goal/account amounts must reject NaN and infinities.

## Import integrity and provenance

Persist value date, counterparty bank code and original identifier; combine Czech domestic number and bank code for canonical identity. Preserve import batch/file/line, bank transaction ID, row balance where available in transaction details. CSV preview exposes every actionable row via pagination, keeping bounded display; changing page does not lose overrides and import examines full file.

Bank ID match in one account is a certain duplicate. Composite matches include canonical amount, currency, direction, dates, description and normalized counterparty. Treat these as possible duplicates with visible control; preserve multiplicity of genuinely identical rows in one file. Reimport/overlap compares occurrence counts against already stored transactions, rather than deduplicating every equal row in memory. Overrides cannot violate unique bank IDs. Pending-to-booked with the same bank ID is promoted safely; pending entries otherwise remain visible and are excluded from actuals. No ID-less data is silently deleted to guess such a promotion.

Deletion is atomic and scoped to batch-owned rows. UI names it “Delete imported transactions…” and shows current linked count and file/period; zero-linked batches use “Delete import record”. Return deleted count. Explain that other imports and separately changed balances/rules remain. Source details make surviving lookalike rows understandable. Do not heuristically link legacy transactions. Restoring deletions should use a safe recoverable batch operation if implemented; otherwise use precise destructive confirmation, without claiming full undo.

Known bank formats open review directly; editable advanced mapping retains manual support. Explain single signed amount vs separate incoming/outgoing amounts, balance, ID, currency and value date. Label account identifier as such, not universally IBAN. Ambiguous dates require an explicit format choice. Sample/template uses selected account currency.

## Budget and report UX

Budget goals are versioned by effective calendar month; changes default to this month and preserve older report limits. Migration backfills existing goals from their creation month, without claiming knowledge of limits before then. Retain current goals in zero-spend categories. Editing without amount changes preserves original value/precision; new values use currency precision. History-based suggestions use only covered completed months and describe sample size; where coverage cannot be proved, say observed data, do not claim completeness.

Cashflow periods compare like lengths: complete 6/12 months or clearly labeled current partial range; YTD compares previous-year YTD through corresponding calendar day, including leap-year handling. Averages identify full observed months and missing/partial periods. Show missing FX/coverage near headline figures. All report errors expose retry; no infinite skeleton. Negative groups remain visible. Add drilldown from cashflow to counted transactions and account scope independent of portfolio `excludeFromBalance`.

Transaction history uses server filters/pagination and provides every row beyond 1,000. Date inputs appear only for custom range. Row/detail shows pending status, flow meaning, both dates, source and complete identifier. Keep MCP setup in integrations, with normal categorization/review usable locally. Account movement labels say Incoming/Outgoing, since transfers are movements too.

Categorization mutations await actual persistence and invalidate transaction/report/goal/drilldown/portfolio keys, then record snapshot and invalidate history. Auto-categorize reports actual successful writes and failures. Learning is explicit opt-in, describes account/payee scope and direction, and changes engine memory only after durable transactional DB update. Category change errors do not close as success or learn accidentally. Broad payee rules must not resurrect after restart.

Planned cashflow is a monthly-equivalent estimate, not a payment calendar. Ignore repaid/expired loans using existing amortization service. Manual items can replace a selected automatic source, avoiding accidental double count, with a visible source relation. Surface estimate/as-of and annual-item normalization.

## Acceptance

Regressions cover each material audit defect: own transfer beats learned merchant; domestic/IBAN equivalence and different banks; custom income/reversal; signed cross-category/cross-month refund conservation; pending exclusion/promotion; FX incompleteness; multi-currency summaries; dedup different currency/payee and repeated occurrence/reimport; >200 preview navigation; atomic batch counts; old balance safeguards; finite validation; versioned limits and no-edit precision; calendar ranges and covered averages; durable learning and repaid loans. Test pure TS utilities and Rust service logic, not React snapshots. Isolated test data only; do not alter the installed app's private database. Run lint/typecheck/TS tests, build, fmt/clippy/Rust tests, and generated binding drift verification. Final report names any unimplemented part explicitly.
