# i18n Standards

The app ships in ten languages via react-i18next: English, Czech, German, Spanish, Italian,
Norwegian (bokmål), Polish, Swedish, Japanese and Simplified Chinese. The list — codes,
native names, Intl format locales, picker order — lives in one place,
`src/i18n/languages.ts`. Locale files live in `src/i18n/locales/<lang>/<namespace>.json`,
one namespace per domain. English (`en`) is the source; Czech (`cs`) is the owner's own
copy and the best guide to intent and tone. Shared terminology: `i18n-glossary.md`.

## 1. Every string lands in EVERY locale

Every user-facing string goes into **all ten** `src/i18n/locales/<lang>/<ns>.json` files in
the same change. **Why:** `fallbackLng: 'en'` (`src/i18n/index.ts`) masks a missing key —
it renders in English and nothing else notices. The gate is `src/i18n/locales.test.ts`
(logic in `locale-parity.ts`): for every locale and namespace it requires the same keys as
English, the plural forms of that language, the same `{{variables}}` and no empty strings.
Write the English and Czech copy yourself; translate the other eight following the glossary.

## 2. Plurals follow the language

i18next picks `_one` / `_few` / `_many` / `_other` / … through `Intl.PluralRules`, so each
locale gives exactly its own forms for every English plural:

| Locale | Forms |
|---|---|
| en, de, nb, sv | `_one` `_other` |
| es, it | `_one` `_many` `_other` (`_many` = the `_other` text; it covers millions) |
| cs | `_one` `_few` `_other` (`_many` optional — decimals) |
| pl | `_one` `_few` `_many` `_other` |
| ja, zh | `_other` only |

Keep a `_zero` key wherever English has one. A key is a plural only when English gives it
at least two suffixed forms — `cat_other` (the "Other" category) is a plain key.

## 3. New namespaces need no registration in the bundle map — but in `NAMESPACES`

Non-English locales are loaded lazily by `import.meta.glob('./locales/*/*.json')`, so a new
namespace file is picked up for them automatically. English is bundled: import the new
`en` file and add the namespace to `NAMESPACES` and the `resources.en` map in
`src/i18n/index.ts`. **Why:** an unregistered namespace makes `t()` return raw keys at
runtime with no build-time error.

## 4. Component usage pattern

```tsx
const { t } = useTranslation('<domain>');       // domain strings
const { t: tc } = useTranslation('common');     // shared strings (buttons, labels)
```

Domain strings live in the domain namespace; generic strings (Save, Cancel, Delete…)
come from `common` — don't duplicate them per domain. Switch the language with
`i18n.changeLanguage(code)` (it loads the lazy chunk first) or `useLanguage().setLanguage`;
use `getFixedT(code)` only after `i18n.loadLanguages(code)` resolved. Pick languages with
`LanguageSelect` (`src/components/common/`), never a segment or one tile per language.
Never branch on `language === 'cs'` for copy — put the text in the locale files.
Month names inside a sentence go through `fmt.monthInSentence` (Intl's own casing per language:
"septiembre de 2026", "October 2026"), never `fmt.month`, which capitalises for labels that start a
line; locale strings may still use `{{x, lower}}`.

## 5. Backend errors are i18n keys

Backend `AppError::Validation` carries i18n keys (e.g. `"validation.bondNameRequired"`),
not English text; `AppError::Auth` does the same for the stable auth keys
`auth.wrongPassword`, `auth.invalidRecoveryKey` and `auth.keyFilesCorrupted` (translated from
the `auth` section of `common.json`; never put file paths in an auth error — log them with
`log::warn!("[AUTH] ...")`). The frontend maps them centrally: `tauriInvoke` throws an
`ApiError` (`src/lib/api-error.ts`, `normalizeApiError`) whose `message` is translated, with
the generic `errors.*` keys of `common.json` standing in for `NotFound`, `Database`,
`ExternalApi`, `Encryption`, `Internal` and unkeyed `Auth` errors — see
`docs/standards/rust-backend.md` rule 3 and `docs/standards/typescript-frontend.md`
rule 6. Adding a new backend validation key means adding its translation to every locale,
same as any other string. Zod form messages follow the same rule: use
`validation.*` keys (e.g. `requiredNumber('validation.amountRequired')` from
`src/utils/form-schemas.ts`), which `FormMessage` translates.

A key that needs values travels with them as JSON after a bar:
`AppError::validation_with("validation.currencyMismatch", json!({"expected": "USD", "actual": "EUR"}))`
serializes to `validation.currencyMismatch|{"actual":"EUR","expected":"USD"}`; `normalizeApiError`
hands the object to `t`, and a value that is itself a key (the stock import's `reason`) is translated
first. The test `validation_errors_carry_keys_never_english_sentences` (`src-tauri/src/error.rs`) fails
on any other `AppError::Validation("…")` literal; `services/mcp/` is exempt because its errors answer
an AI client.

## 6. Layout survives long and CJK copy

German runs about 30 % longer than English; Japanese and Chinese have no word spaces.
Give text containers `min-w-0` + `truncate` or let them wrap; never size a button or tab
to fit the English label. `<html lang>` follows the UI language, and `index.css` resets
the negative tracking and names the CJK system fonts under `:lang(ja)` / `:lang(zh)`.

## 7. Verification

```bash
npx vitest run src/i18n/
```

runs the parity gate for every locale (it is also part of `npm test`).
